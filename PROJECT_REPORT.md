# 📄 Project Technical Report: Trip Spark

**Developer:** Solo Implementation
**Version:** 1.0.0
**Project Goal:** To bridge the gap between AI-generated travel ideas and actionable, data-backed travel logistics.

---

## 1. System Architecture

The application follows a modern **Decoupled Architecture** to ensure scalability and ease of maintenance.

### High-Level Data Flow:
1.  **Frontend (React/Vite)**: Captures user intent (destination, dates, budget, vibe).
2.  **Backend (Express/Node.js)**: Processes the request, validates data with **Zod**, and orchestrates two primary external service calls.
3.  **Intelligence Layer (Google Gemini)**: Receives a strictly formatted prompt to return a structured JSON itinerary.
4.  **Environmental Layer (Open-Meteo)**: Fetches historical/forecast weather data based on the geocoded destination.
5.  **Persistence Layer (PostgreSQL/Prisma)**: Stores the combined AI + Weather data into a relational database for future retrieval.

---

## 2. Technical Decision Log

### 🧠 Generative AI: Google Gemini Pro
**Decision:** Used `@google/generative-ai` for prompt engineering.
**Reason:** Gemini Pro offers a larger context window and better native JSON formatting stability compared to other models in its class, which is critical for complex 5-10 day itineraries.

### 💾 Database: PostgreSQL + Prisma ORM
**Decision:** Relational DB with a type-safe ORM.
**Reason:** Travel plans are highly structured. Prisma provides "Type-Safety from Schema to Script," ensuring that the JSON generated by the AI matches our database storage expectations without runtime errors.

### 🔐 Auth: Firebase Identity Platform
**Decision:** Outsourced authentication logic to Firebase.
**Reason:** As a solo developer, handling security (JWT rotations, password hashing, OAuth handshakes) is high-risk. Firebase handles the security overhead, allowing me to focus on the core travel features.

## 3. Database Schema Overview

We use two primary models:
- **User**: Stores profile data and links to created trips.
- **TripPlan**: The core entity. It stores:
    - Metadata (Destination, Dates).
    - `plan`: A large JSON block containing the full itinerary.
    - `weather`: A JSON block containing day-by-day forecast data.
    - `shareId`: A unique CUID for public sharing without exposing the internal ID.

---

## 4. Key Implementation Challenges

### Challenge: AI JSON Reliability
**Problem:** LLMs sometimes return markdown or "hallucinate" the JSON structure.
**Solution:** I implemented a custom **JSON Extraction Layer** that uses Regex to strip markdown backticks and a **Zod Validation Layer** that verifies the AI's response before saving it to the database. If the AI fails the schema check, the system automatically retries or returns a graceful error.

### Challenge: Prisma JSON Typing
**Problem:** TypeScript treats JSON columns as `any` by default.
**Solution:** Defined strict interfaces for `TripPlanResponse` and used TypeScript casting (`as unknown as Prisma.InputJsonValue`) to ensure full type-safety throughout the API.
